# План разработки прототипа кооперативной FPS-защиты крепости

## 1. Цель проекта

Создать прототип стилизованной игры от первого лица, вдохновлённой игровым циклом Zombs.io:

1. Игрок собирает дерево и камень.
2. Устанавливает центральное Ядро крепости.
3. Строит экономические и оборонительные сооружения.
4. Получает золото из шахт.
5. Улучшает Ядро, постройки и оружие.
6. Днём готовит крепость.
7. Ночью вместе с башнями отражает всё более крупные волны противников.
8. Проигрывает при уничтожении Ядра.

Первый полноценный прототип должен представлять собой законченный одиночный забег продолжительностью 15–20 минут. Архитектура должна допускать последующее добавление host-authoritative multiplayer, но мультиплеер реализуется только после проверки одиночного игрового цикла.

Главный принцип:

> Каждый этап должен завершаться запускаемым и проверяемым билдом, а не накоплением систем «на будущее».

## 4. Архитектурные правила

### 4.1. Fixed timestep

Игровая симуляция работает с фиксированным шагом 60 Гц:

```text
получить ввод
накопить frame time

пока накопленного времени достаточно:
    выполнить SimulationTick(1/60)
    уменьшить накопленное время

отрисовать интерполированное состояние
```

Отрисовка может происходить с любой частотой. Скорость игрока, ИИ, экономика, волны и снаряды не должны зависеть от FPS.

### 4.2. Разделение симуляции и отображения

Симуляция не должна:

- загружать модели;
- вызывать функции отрисовки raylib;
- напрямую проигрывать звуки;
- читать клавиатуру и мышь;
- создавать частицы;
- управлять визуальной тряской камеры.

Симуляция изменяет игровой мир и формирует события:

```cpp
BuildingDestroyedEvent
EnemyKilledEvent
WaveStartedEvent
WaveCompletedEvent
ProjectileHitEvent
ResourceCollectedEvent
CoreDamagedEvent
RunEndedEvent
```

Слой представления читает события и создаёт:

- звук;
- частицы;
- вспышки;
- визуальные обломки;
- тряску камеры;
- элементы HUD.

### 4.3. Команды

Интерфейс и игрок не должны напрямую изменять состояние мира. Все значимые действия проходят через команды:

```cpp
PlaceBuildingCommand
UpgradeBuildingCommand
RepairBuildingCommand
SellBuildingCommand
StartRunCommand
StartWaveEarlyCommand
FireWeaponCommand
UseConsumableCommand
```

Симуляция проверяет команду и принимает либо отклоняет её. Такой подход необходим для будущего авторитетного сетевого хоста.

### 4.4. Data-driven контент

Характеристики игрового контента должны храниться в JSON:

```text
assets/data/buildings.json
assets/data/enemies.json
assets/data/weapons.json
assets/data/waves.json
assets/data/economy.json
assets/data/gameplay.json
```

В данных находятся:

- здоровье;
- урон;
- дальность;
- стоимость;
- скорость;
- время перезарядки;
- радиус;
- уровни улучшений;
- ссылки на модели;
- ссылки на звуки;
- визуальные параметры.

В коде находится поведение систем.

### 4.5. Идентификаторы сущностей

Не хранить долгоживущие сырые указатели между системами. Использовать стабильные идентификаторы:

```cpp
struct EntityId {
    uint32_t index;
    uint32_t generation;
};
```

Это позволяет обнаруживать обращения к уже уничтоженным объектам и упрощает сетевую синхронизацию.

## 12. Фаза 6 — навигация и массовый ИИ

Оценка: 8–12 дней.

Не использовать отдельный A* для каждого противника.

### 12.1. Навигационная сетка

```cpp
struct NavCell {
    float terrainCost;
    EntityId buildingId;
    float distanceToCore;
};
```

Размер клетки: 0,75–1 метр.

### 12.2. Flow field

После изменения крепости:

1. Навигационное поле помечается грязным.
2. От Ядра запускается Dijkstra.
3. Земля получает обычную стоимость.
4. Ловушка получает повышенную стоимость.
5. Стена получает высокую, но не бесконечную стоимость.
6. Для каждой клетки вычисляется направление уменьшения стоимости.

Конечная стоимость стен позволяет противникам выбирать наиболее выгодное место для пролома.

Поле пересчитывается:

- после установки здания;
- после продажи;
- после разрушения;
- после изменения ворот.

Не пересчитывать поле каждый кадр.

### 12.3. Состояния противника

```text
Spawn
MoveToCore
AttackBuilding
AttackCore
Stagger
Dead
```

Противник:

- читает направление flow field;
- движется к следующей клетке;
- учитывает локальное расхождение;
- атакует здание в следующей клетке;
- после разрушения продолжает движение.

### 12.4. Локальное избегание

- Найти соседей через spatial hash.
- Добавить небольшую силу расхождения.
- Ограничить максимальную коррекцию.
- Допустить небольшое пересечение моделей.

Плотная читаемая орда важнее идеальной физики.

### 12.5. Пулы

Заранее выделить память минимум на:

- 200 противников;
- 300 снарядов;
- 500 эффектов.

Во время обычной волны не должно быть частых `new/delete`.

### 12.6. Spatial hash

Использовать uniform spatial hash для:

- поиска соседей;
- выбора целей башнями;
- расчёта взрывов;
- атак игрока;
- поиска ближайших противников.

### 12.7. Definition of Done

- 100 противников находят Ядро.
- Они используют открытый проход.
- Они атакуют стену, если путь перекрыт.
- После разрушения маршрут обновляется.
- Отсутствуют систематически застревающие противники.
- ИИ укладывается в установленный бюджет времени.

- fire;
- magical.

Сопротивления можно пока не реализовывать.

### 13.2. Кирка

- Добывает ресурсы.
- Слабо повреждает противников.
- Использует raycast.

### 13.3. Основное оружие

Арбалет или ружьё:

- дальняя атака;
- hitscan или быстрый снаряд;
- перезарядка;
- отдача;
- разброс;
- звуки;
- hit marker.

### 13.4. Бомба

- Физический бросок.
- Таймер.
- Урон по площади.
- Отбрасывание.
- Ограниченный запас.

### 13.5. Стрелковая башня

- Ищет ближайшую цель.
- Поворачивается.
- Стреляет в одну цель.
- Имеет высокую скорострельность.

### 13.6. Пушка

- Выбирает центр группы.
- Медленно стреляет.
- Выпускает физический снаряд.
- Взрыв повреждает нескольких врагов.
- Сильно отбрасывает.
- Создаёт звук и тряску.

### 13.7. Ловушка

- Активируется по площади.
- Замедляет.
- Имеет cooldown.
- Изнашивается или требует ремонта.

### 13.8. Выбор целей

Башни не должны каждый кадр перебирать всех противников.

- Использовать spatial hash.
- Обновлять поиск несколько раз в секунду.
- Хранить текущую цель.
- Переключаться после смерти или выхода цели из радиуса.

### 13.9. Definition of Done

Игрок и башни совместно отбивают волну. Игрок полезен, но:

- башни не выигрывают автоматически;
- оружие не делает строительство ненужным.

## 14. Фаза 8 — директор волн и баланс

Оценка: 5–7 дней.

### 14.1. Бюджет

Пример стоимости:

```text
обычный противник = 1
быстрый = 2
тяжёлый = 5
босс = 30
```

Пример бюджета:

```text
Волна 1: 15
Волна 2: 25
Волна 3: 40
Волна 4: 55
Волна 5: 75
Волна 6: 100 + босс
```

### 14.2. Обычный противник

- Средняя скорость.
- Среднее здоровье.
- Основа орды.

### 14.3. Быстрый

- Низкое здоровье.
- Высокая скорость.
- Использует оставленные проходы.

### 14.4. Тяжёлый

- Медленный.
- Высокое здоровье.
- Повышенный урон зданиям.
- Пониженное отбрасывание.

### 14.5. Босс

- Очень крупный силуэт.
- Таранный удар.
- Понятная подготовка атаки.
- Может проломить слабую стену.
- Не появляется вплотную к базе.

### 14.6. Директор

Директор:

- выбирает направления атаки;
- предупреждает игрока;
- создаёт группы;
- не создаёт врагов непосредственно в поле зрения;
- чередует давление и короткие паузы;
- увеличивает сложность по конфигурации.

### 14.7. Экономика

Игрок должен выбирать между:

- башней сейчас;
- шахтой для будущего дохода;
- улучшением Ядра;
- ремонтом;
- собственным оружием.

Если всегда выгодно немедленно строить максимум шахт, экономика требует переработки.

### 14.8. Definition of Done

После знакомства хороший игрок проходит прототип примерно в 50–70% забегов. Допустимы разные формы крепости.

## 15. Фаза 9 — интерфейс и обучение

Оценка: 4–6 дней.

### 15.1. HUD

Показывать:

- здоровье игрока;
- дерево;
- камень;
- золото;
- здоровье Ядра;
- текущую волну;
- время до ночи;
- выбранную постройку;
- стоимость;
- направление повреждения крепости.

### 15.2. Обучение

Использовать короткие контекстные задачи:

```text
Ударьте дерево киркой
Соберите 30 дерева
Установите Ядро
Постройте золотую шахту
Подготовьтесь: ночь через 30 секунд
```

После первой волны подсказки исчезают.

### 15.3. Отладочная панель

Создать собственную минимальную панель:

- начать волну;
- уничтожить всех врагов;
- выдать ресурсы;
- включить бессмертие;
- показать flow field;
- показать spatial hash;
- замедлить время;
- создать тип врага;
- повредить Ядро;
- скрыть HUD;
- сохранить screenshot.

### 15.4. Definition of Done

Новый тестировщик без объяснения запускает первую ночь максимум за пять минут.

## 16. Фаза 10 — визуальный vertical slice

Оценка: 3–6 недель параллельно с моделированием.

### 16.1. Asset pipeline

Для каждого объекта определить:

- единицы Blender в метрах;
- направление осей;
- положение origin;
- максимальный размер;
- количество материалов;
- правила именования;
- коллизионный объём;
- LOD;
- socket выстрела;
- socket эффектов;
- имена анимаций.

Пример:

```text
tower_cannon.glb
socket_muzzle
socket_base
collision_box
```

### 16.2. Приоритет моделей

1. Ядро.
2. Стена.
3. Ворота.
4. Пушка.
5. Обычный противник.
6. Босс.
7. Шахта.
8. Остальные здания.
9. Оружие.
10. Окружение.

### 16.3. Анимации

Минимальный набор:

- idle;
- run;
- attack;
- hit;
- death.

Не создавать полноценный ragdoll для каждого противника. После смерти:

- проиграть короткую анимацию;
- применить визуальный импульс;
- заменить упрощённым телом либо растворить;
- удалить через несколько секунд.

### 16.4. Освещение

Для прототипа:

- один направленный свет;
- несколько дешёвых источников вокруг Ядра;
- emissive-материалы;
- туман;
- градиент неба;
- baked AO;
- одна простая shadow map либо минимальные тени.

Не начинать с полноценного PBR и множества динамических теней.

### 16.5. Эффекты

Приоритет:

- muzzle flash;
- след снаряда;
- взрыв;
- искры;
- падение дерева;
- каменные осколки;
- повреждение стены;
- удар босса;
- уничтожение Ядра;
- светящиеся глаза орды.

### 16.6. Definition of Done

Из обычного игрового процесса можно записать минимум пять понятных коротких роликов без постановочного редактирования.

## 17. Фаза 11 — оптимизация

Оценка: 1–2 недели.

Оптимизировать только после профилирования.

### 17.1. Бюджеты

- 60 FPS в 1080p на выбранной тестовой машине.
- 150 активных противников.
- Simulation tick до 5 мс.
- Навигация до 2 мс.
- Логика башен до 1 мс.
- Отсутствие выделений памяти во время обычной волны.
- Загрузка карты до 10 секунд.

### 17.2. Частота обновления ИИ

- Рядом с игроком — каждый tick.
- Средняя дистанция — через tick.
- Далеко — 10–15 раз в секунду.
- За пределами видимости — упрощённая анимация и логика.

### 17.3. Рендеринг

- Общие модели.
- Общие материалы.
- Texture atlas.
- Instancing одинаковых объектов.
- Frustum culling.
- Простые LOD.
- Ограничение количества частиц.
- Удаление обломков через 2–4 секунды.
- Фиксированный лимит следов попаданий.

Instancing вводится только при подтверждённом bottleneck.

### 17.4. Gate A

Переходить к мультиплееру только если:

- одиночный цикл интересен;
- строительство удобно;
- орда выглядит убедительно;
- после поражения хочется переиграть;
- игра уже создаёт пригодные для роликов ситуации.

Если условия не выполнены, исправляется игровой цикл, а не добавляется сеть.

## 18. Фаза 12 — сетевой эксперимент

Оценка: 1–2 недели.

Создать отдельную техническую сцену:

- два игрока;
- одна стена;
- один противник;
- одно Ядро;
- одна команда строительства.

### 18.1. Модель сети

- Listen server.
- Один игрок является хостом.
- Хост авторитетен.
- Клиент отправляет ввод и команды.
- Хост изменяет игровой мир.
- Клиент интерполирует snapshots.

Не использовать deterministic lockstep.

### 18.2. Надёжные сообщения

- Подключение.
- Установка здания.
- Улучшение.
- Продажа.
- Разрушение.
- Начало волны.
- Изменение общих ресурсов.
- Смерть.
- Возрождение.

### 18.3. Ненадёжные sequenced-сообщения

- Позиция.
- Направление взгляда.
- Скорость.
- Состояние оружия.
- Позиции противников.

### 18.4. Частоты

- Симуляция хоста — 60 Гц.
- Ввод клиента — 30 Гц.
- Snapshot мира — 10–20 Гц.
- Интерполяция — 100–150 мс.

### 18.5. Definition of Done

При искусственной задержке 100–150 мс:

- игроки перемещаются приемлемо;
- обе стороны видят одну стену;
- ресурсы совпадают;
- противник умирает одинаково;
- команды не дублируются.

Переподключение пока не требуется.

## 21. Организация работы ИИ-агентов

### 21.1. Один оркестратор

Только один агент или человек отвечает за:

- архитектуру;
- изменение публичных интерфейсов;
- объединение веток;
- приоритеты;
- Definition of Done;
- разрешение конфликтов.

### 21.2. Формат задания

Каждое задание должно содержать:

```text
Цель
Контекст
Разрешённые файлы
Запрещённые изменения
Публичный интерфейс
Acceptance criteria
Команды сборки и тестов
Ожидаемый результат
```

Пример:

```text
Цель:
Реализовать расчёт flow field от Ядра.

Разрешённые файлы:
src/navigation/*
tests/navigation/*

Запрещено:
Менять BuildingSystem, EnemySystem и публичный CMake API.

Интерфейс:
FlowField BuildFlowField(const NavGrid&, GridPosition target);

Критерии:
- обходит постоянные препятствия;
- использует повышенную стоимость стен;
- результат одинаков при одинаковом вводе;
- есть минимум пять модульных тестов;
- проект собирается без новых warnings.
```

### 21.3. Размер задач

Хорошая задача:

- один компонент;
- один публичный интерфейс;
- 1–3 файла реализации;
- тесты;
- объём до одного рабочего дня.

Плохая задача:

```text
Реализуй систему врагов.
```

Правильное разбиение:

1. Добавить `EnemyDefinition`.
2. Добавить пул противников.
3. Добавить состояния.
4. Добавить spatial hash.
5. Добавить движение по flow field.
6. Добавить атаку здания.
7. Добавить получение урона.
8. Добавить death event.
9. Добавить debug rendering.
10. Добавить нагрузочный тест.

### 21.4. Правила для агентов

- Не менять архитектуру без отдельного ADR.
- Не добавлять зависимости самостоятельно.
- Не оставлять TODO вместо результата.
- Не подавлять warnings.
- Не создавать абстракции для единственного использования.
- Не переписывать соседние системы «заодно».
- Перед завершением запускать сборку и тесты.
- Перечислять изменённые публичные интерфейсы.
- Объяснять спорные решения.
- Не форматировать несвязанные файлы.
- Не смешивать рефакторинг и новую функцию в одной задаче.

### 21.5. Параллельная работа

Можно параллелить:

- модели и программирование;
- аудио и UI;
- игровые JSON и rendering;
- тесты навигации и визуальные эффекты.

Нельзя независимо изменять:

- `Simulation`;
- систему ID;
- формат событий;
- команды;
- схему сохранения;
- сетевой протокол;
- общую JSON-схему.

## 24. Главные риски

### 24.1. Слишком ранний мультиплеер

Сеть может поглотить месяцы до того, как станет понятно, интересна ли сама игра.

Решение: сначала закончить `Core Loop`, но с командами, событиями и fixed timestep.

### 24.2. Массовый ИИ

Отдельный pathfinding и полноценная анимация каждого противника могут уничтожить производительность.

Решение:

- flow field;
- spatial hash;
- object pools;
- разные частоты обновления;
- instancing после профилирования.

### 24.3. Строительство неудобно в FPS

Если одну стену трудно поставить, игрок не станет проектировать крепость.

Решение:

- сетка;
- магнитное соединение;
- быстрые preview;
- минимум ограничений;
- установка менее чем за секунду.

### 24.4. Игрок становится лишним

Слишком сильные башни превращают FPS в наблюдение.

Решение:

- башни контролируют массу;
- игрок устраняет приоритетные угрозы;
- игрок чинит прорывы;
- оружие игрока и постройки усиливают друг друга.

### 24.5. Добыча становится рутиной

Долгое рубление разрушает темп.

Решение:

- быстрые ресурсные узлы;
- улучшение инструмента;
- шахты и автоматические сборщики;
- меньшая роль ручной добычи в поздних волнах.

### 24.6. Generic asset flip

Реалистичные зомби и стандартные модели плохо выделяются.

Решение:

- единый low-poly стиль;
- собственные силуэты;
- необычные противники;
- яркое Ядро;
- узнаваемые башни;
- выразительные эффекты разрушения.

## 25. Финальные критерии успеха прототипа

Разработку стоит продолжать, если:

- игрок понимает цель без длинного объяснения;
- первая ночь начинается не позднее пятой минуты;
- установка стены занимает меньше секунды;
- игрок понимает причину поражения;
- после поражения хочет изменить крепость;
- игроки самостоятельно создают коридоры и ловушки;
- орда читается в коротком ролике;
- 100–150 противников работают стабильно;
- кооператив усиливает веселье;
- игра создаёт истории о прорывах и спасении Ядра.

Плохие признаки:

- основное время занимает добыча;
- башни делают игрока ненужным;
- оружие делает строительство ненужным;
- противники застревают;
- существует одна заведомо лучшая база;
- ночью невозможно определить место прорыва;
- визуально игра похожа на generic zombie shooter.

## 26. Следующий практический шаг

Первой задачей после создания репозитория должен быть milestone `One Night`.

Необходимо реализовать минимальную цепочку:

```text
FPS-перемещение
→ добыча дерева
→ установка Ядра
→ строительство стены
→ появление противников
→ движение к Ядру
→ атака стены
→ разрушение Ядра или победа
```

Пока эта цепочка не стала понятной и потенциально интересной, не следует добавлять:

- мультиплеер;
- сложные модели;
- Steamworks;
- большую экономику;
- дополнительные биомы;
- метапрогрессию.
