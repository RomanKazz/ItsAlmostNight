Ты работаешь над существующей игрой на C++20 + raylib. Это first-person survival / tower-defense игра, вдохновлённая Zombs.io, Raft и строительством Fortnite.

Текущая задача: поэтапно реализовать процедурный неровный ландшафт и модульную многоэтажную строительную систему. Настоящих 3D-моделей пока нет — используй кубы, параллелепипеды, линии и другие примитивы raylib.

Все существующие постройки имеют footprint только двух размеров:

- 1×1 клетка;
- 2×2 клетки.

Не добавляй прямоугольные footprint 1×2, 2×1 и произвольные размеры. Архитектура должна позволять в будущем добавлять модели GLB без переписывания строительной логики.

Работай автономно и по фазам. Перед изменениями полностью изучи существующую структуру проекта, CMake, системы строительства, коллизий, сущностей, игрового мира и рендера. Не переписывай работающие системы без необходимости. После каждой фазы собирай проект, запускай доступные тесты и исправляй ошибки.

Не переходи к следующей фазе, если проект не компилируется.

## Основная концепция

Игровой ландшафт процедурный и неровный. Постройки не наклоняются по нормали поверхности. Они устанавливаются на горизонтальную дискретную строительную сетку.

Если земля под постройкой неровная, под полом автоматически появляются вертикальные опоры, доходящие до поверхности земли.

Пример:

    горизонтальный пол
    ┌──────────────┐
    │              │
    └──────────────┘
      │    │     │
      │    │     │
    земля неровная

Строительство должно поддерживать несколько этажей:

- фундамент или платформа;
- пол;
- стены;
- колонны;
- лестницы/рампы;
- следующий этаж;
- обычные здания размером 1×1 или 2×2.

Для первой версии ограничить строительство тремя этажами, но не зашивать это ограничение глубоко в архитектуру.

## Конфигурация

Все основные параметры должны находиться в одном конфигурационном объекте или файле:

- cellSize;
- verticalGridStep;
- storeyHeight;
- maxStoreys;
- maxWoodSupportLength;
- terrainResolution;
- terrainWorldSize;
- terrainAmplitude;
- terrainFrequency;
- terrainSeed;
- coreFlatRadius;
- buildPreviewDistance;
- minimumGroundClearance.

Рекомендуемые начальные значения:

- cellSize = 2.0;
- verticalGridStep = 0.5;
- storeyHeight = 2.5;
- maxStoreys = 3;
- maxWoodSupportLength = 4.0;
- minimumGroundClearance = 0.1–0.15;
- buildPreviewDistance = 8–10 метров.

Если в проекте уже существует размер строительной клетки, используй его как источник истины.

## Архитектурные требования

Раздели систему минимум на следующие логические части:

1. TerrainHeightfield
   - хранит высоты;
   - генерирует terrain по seed;
   - возвращает высоту в любой мировой позиции XZ;
   - возвращает приближённую нормаль;
   - проверяет границы карты;
   - является источником истины для физики и строительства.

2. TerrainRenderer
   - создаёт и рисует меш из TerrainHeightfield;
   - не содержит игровой логики;
   - при необходимости перестраивает меш.

3. BuildGrid
   - преобразует мировые координаты в дискретные GridCoord;
   - поддерживает X, Z и вертикальный уровень;
   - умеет вычислять мировую позицию центра клетки;
   - хранит занятые клетки;
   - отдельно учитывает объём постройки, пол, стены и структурные узлы.

4. BuildingDefinition
   - идентификатор типа;
   - footprint: только 1×1 или 2×2;
   - высота в уровнях;
   - категория;
   - правила поддержки;
   - параметры placeholder-рендера;
   - параметры коллизии;
   - стоимость, если система ресурсов уже существует.

5. BuildingInstance
   - уникальный ID;
   - ID определения;
   - координата сетки;
   - поворот;
   - footprint;
   - уровень;
   - здоровье;
   - состояние поддержки;
   - список созданных опор;
   - transform для рендера.

6. PlacementValidator
   - проверяет занятость клеток;
   - пересечение с terrain;
   - пересечение с игроком;
   - максимальную длину опор;
   - наличие поддержки для верхних этажей;
   - границы карты;
   - корректность footprint 1×1 или 2×2;
   - возвращает не только bool, но и конкретную причину ошибки.

7. SupportSystem
   - создаёт опоры под платформами;
   - переиспользует общие угловые опоры соседних полов;
   - хранит количество зависимых элементов;
   - определяет наличие пути поддержки до земли;
   - не занимается полноценной физической симуляцией.

8. BuildingRenderer
   - пока рисует placeholder-геометрию;
   - цвет зависит от типа постройки;
   - не содержит правил установки;
   - в будущем должен позволить заменить примитив на GLB-модель.

Не создавай один огромный BuildingManager, выполняющий всю логику, рендер, ввод и физику одновременно.

## Фаза 1. Инспекция и план интеграции

До редактирования:

1. Изучи структуру проекта.
2. Найди существующие:
   - систему строительства;
   - структуры построек;
   - коллайдеры;
   - управление игроком;
   - terrain/ground;
   - сохранение мира;
   - pathfinding;
   - тесты.
3. Зафиксируй, какие компоненты можно переиспользовать.
4. Составь короткий план изменений с конкретными файлами.
5. Проверь текущее состояние сборки до изменений.

Не удаляй существующие возможности игры.

## Фаза 2. Процедурный Heightfield

Реализуй детерминированный ландшафт, зависящий от seed.

Используй несколько слоёв smooth noise / fractal noise:

- крупные плавные формы;
- средние холмы;
- очень слабые мелкие неровности.

Избегай частых острых пиков.

Область вокруг ядра должна плавно выравниваться:

- внутри coreFlatRadius почти плоско;
- между coreFlatRadius и внешним радиусом плавное смешивание;
- не должно быть резкой круглой ступени.

Добавь методы примерно такого назначения:

- Generate(seed);
- GetHeight(worldX, worldZ);
- GetNormal(worldX, worldZ);
- IsInside(worldX, worldZ);
- GetMinMaxHeight();

GetHeight должен использовать билинейную интерполяцию между точками heightfield.

Меш terrain должен полностью соответствовать данным GetHeight.

Добавь debug-переключатели:

- wireframe terrain;
- отображение seed;
- отображение центральной плоской зоны;
- регенерация карты с новым seed;
- регенерация с тем же seed.

Критерии:

- одинаковый seed создаёт одинаковую карту;
- игрок корректно ходит по поверхности;
- центральная зона пригодна для установки ядра;
- terrain не содержит дыр и разрывов;
- проект компилируется.

## Фаза 3. Строительная сетка

Реализуй глобальную сетку XZ и дискретные вертикальные уровни.

Вертикальная координата должна быть кратна verticalGridStep. Полноценный этаж равен storeyHeight.

Введи типы:

- GridCoord { x, yLevel, z };
- Footprint { OneByOne, TwoByTwo };
- Rotation { Deg0, Deg90, Deg180, Deg270 }.

Для footprint:

- 1×1 занимает одну клетку;
- 2×2 занимает четыре клетки;
- anchor должен использовать единое документированное правило;
- поворот не меняет footprint 2×2, но должен сохраняться для будущих моделей.

Добавь unit-тесты или assert-проверки:

- world → grid → world;
- отрицательные координаты;
- footprint 1×1;
- footprint 2×2;
- проверка пересечений;
- освобождение клеток после удаления.

## Фаза 4. Первая фундаментная платформа

Добавь placeholder-постройку FoundationFloor размером 1×1.

Установка:

1. Игрок направляет прицел на terrain.
2. Выполняется raycast.
3. Позиция привязывается к XZ-сетке.
4. Из четырёх углов клетки берётся высота terrain.
5. Высота верхней поверхности определяется по самому высокому углу.
6. Высота округляется вверх до verticalGridStep.
7. Добавляется minimumGroundClearance.
8. Создаются четыре вертикальные опоры до земли.

Платформа всегда горизонтальная.

Отображение:

- верхняя рама — тонкие балки;
- пол — несколько простых досок или один коричневый куб;
- опоры — узкие вертикальные кубы;
- при большой длине опор добавить визуальные диагональные распорки.

Опоры должны масштабироваться только по вертикали.

Если длина хотя бы одной опоры превышает maxWoodSupportLength, установка запрещена.

Если terrain пересекает объём пола или верхней рамы, установка запрещена или платформа автоматически поднимается на следующий verticalGridStep.

## Фаза 5. Preview и причины невозможности установки

Добавь полноценный ghost-preview:

- зелёный — можно установить;
- красный — нельзя;
- жёлтый — допустимо, но требует длинных опор;
- полупрозрачный материал;
- placeholder опор тоже отображается в preview.

Показывай краткую причину:

- место занято;
- слишком далеко;
- слишком длинные опоры;
- пересечение с terrain;
- пересечение с игроком;
- нет поддержки;
- превышен максимальный этаж;
- за пределами карты.

Нельзя устанавливать постройку, если её collider пересекает капсулу игрока с дополнительным запасом 0.2–0.3 м.

Preview не должен добавляться в occupancy и не должен иметь физической коллизии.

## Фаза 6. Платформы 2×2

Добавь FoundationFloor размером 2×2.

Правила:

- занимает четыре клетки;
- создаёт верхнюю раму размером 2×2 клетки;
- опоры располагаются минимум по четырём внешним углам;
- при необходимости можно добавить центральную опору как параметр BuildingDefinition;
- проверка terrain выполняется по всем углам footprint;
- верх остаётся горизонтальным.

Не копируй логику 1×1 отдельным большим кодом. Используй общий алгоритм footprint.

## Фаза 7. Общие опоры

Опоры должны храниться в угловых узлах сетки.

Если соседние платформы используют один и тот же угол:

- не создавай две визуальные опоры в одной позиции;
- увеличь reference count;
- вычисли необходимую верхнюю и нижнюю точки;
- при удалении платформы уменьши reference count;
- удали опору только тогда, когда она больше никому не нужна.

Добавь debug-отображение ID опор и количества зависимостей.

## Фаза 8. Верхние этажи

Добавь обычный Floor, который устанавливается на существующий каркас, колонны или стены.

Правила:

- этажи располагаются с шагом storeyHeight;
- верхний Floor не создаёт опоры до terrain, если под ним уже существует структурная поддержка;
- максимальная высота прототипа — maxStoreys;
- пол нельзя устанавливать в воздух без пути поддержки;
- 1×1 и 2×2 используют один общий алгоритм.

Добавь placeholder Column:

- занимает структурный узел;
- соединяет два вертикальных уровня;
- позволяет поддерживать следующий этаж;
- визуально является узким кубом;
- тонкие опоры пока не обязаны блокировать игрока.

## Фаза 9. Стены и лестницы

Добавь:

- Wall 1×1;
- Wall 2×2, если такой тип уже существует в текущей игре;
- Ramp/Stairs 1×1;
- при необходимости Ramp/Stairs 2×2.

Если существующие стены уже реализованы, интегрируй их в новую вертикальную сетку, не создавая дубликат системы.

Стены:

- устанавливаются только на поддержанный пол или фундамент;
- имеют нормальную коллизию игрока и мобов;
- снапятся по повороту 90 градусов;
- не наклоняются вместе с terrain.

Лестницы:

- соединяют два соседних уровня;
- визуально могут быть наклонным параллелепипедом;
- физическая поверхность должна быть простой рампой, а не набором отдельных ступеней;
- игрок должен плавно подниматься без постоянных прыжков;
- лестница не должна пересекать terrain или другие постройки.

## Фаза 10. Placeholder-рендер

Используй понятную цветовую схему:

- фундамент — тёмное дерево;
- пол — светлое дерево;
- опоры — коричневые;
- стены — оранжево-коричневые;
- лестницы — светлые;
- неподдерживаемые элементы — красные;
- выбранный элемент — контур или яркая подсветка.

Избегай создания отдельного GPU-ресурса для каждого экземпляра. Переиспользуй общие меши/модели примитивов, где это возможно.

Рендер должен быть отделён от данных, чтобы позже заменить:

- DrawCube → DrawModel;
- placeholder → GLB;
- без изменения BuildGrid и PlacementValidator.

## Фаза 11. Упрощённая структурная поддержка

Создай граф поддержки.

Элемент считается поддержанным, если существует путь:

- элемент;
- пол/балка;
- колонна/стена/опора;
- фундамент;
- terrain.

При удалении или разрушении элемента:

1. Отметь зависимые элементы dirty.
2. Пересчитай только затронутую область.
3. Не обходи весь мир каждый кадр.
4. Неподдерживаемые элементы переходят в состояние Unsupported.
5. Через настраиваемую задержку они получают урон или удаляются.

На первой версии не нужна физика падающих построек. Можно:

- кратко трясти placeholder;
- изменить цвет;
- через 1–2 секунды заменить на несколько временных кубов-обломков;
- удалить зависимый элемент.

Добавь возможность полностью отключить разрушение через debug-настройку.

## Фаза 12. Коллизии и передвижение

Правила коллизий:

- полы поддерживают игрока;
- стены блокируют игрока;
- лестницы являются рампами;
- большие здания блокируют игрока;
- тонкие опоры можно не учитывать в коллизии игрока;
- preview не имеет коллизии;
- декоративные балки не имеют коллизии;
- gameplay collider не должен повторять сложную форму рендера.

Игрок должен:

- корректно стоять на этажах;
- не проваливаться между соседними полами;
- плавно переходить между клетками;
- подниматься по лестнице;
- не застревать на декоративных балках;
- не телепортироваться при установке постройки.

## Фаза 13. Удаление и перестройка

Добавь безопасное удаление:

- освобождение всех занятых клеток;
- обновление общих опор;
- пересчёт поддержки зависимых элементов;
- удаление collider;
- удаление render instance;
- возврат ресурсов, если это уже поддерживает игра.

Нельзя оставлять висячие ID, collider или ссылки на уничтоженные элементы.

Добавь debug-команду очистки всех построек без перегенерации terrain.

## Фаза 14. Сохранение

Если в проекте уже существует сохранение мира, добавь:

- terrainSeed;
- BuildingInstance;
- GridCoord;
- footprint;
- rotation;
- уровень;
- здоровье;
- тип постройки.

Не сохраняй автоматически вычисляемые опоры, если их можно детерминированно восстановить после загрузки.

После загрузки:

1. Восстановить terrain по seed.
2. Восстановить постройки.
3. Восстановить occupancy.
4. Пересоздать опоры.
5. Пересчитать поддержку.
6. Пересоздать colliders.

Если сохранения пока нет, оставь чистый сериализуемый DTO, но не внедряй стороннюю библиотеку только ради этой фазы.

## Тесты

Добавь тесты для чистой логики:

- детерминированность terrain;
- билинейная высота;
- преобразование координат;
- footprint 1×1 и 2×2;
- overlap;
- размещение на четырёх разных высотах;
- максимальная длина опоры;
- общая опора соседних полов;
- удаление одной из соседних платформ;
- поддержанный второй этаж;
- неподдержанный второй этаж;
- освобождение occupancy;
- загрузка/восстановление, если есть сохранения.

Графические и input-зависимые части тестировать вручную через debug-сцену.

## Debug UI

Добавь компактную debug-панель:

- terrain seed;
- regenerate same seed;
- regenerate random seed;
- show terrain wireframe;
- show build grid;
- show occupied cells;
- show structural links;
- show colliders;
- show support pillars;
- disable structural collapse;
- выбранный footprint: 1×1 / 2×2;
- текущий вертикальный уровень;
- причина невалидного preview;
- количество построек;
- количество общих опор.

Используй существующий UI проекта. Не добавляй тяжёлую зависимость только для debug-панели.

## Производительность

Не выполняй каждый кадр:

- полный пересчёт структурного графа;
- полный поиск всех построек;
- регенерацию terrain;
- создание и уничтожение GPU-мешей;
- выделение большого количества временной памяти.

Используй:

- dirty-флаги;
- spatial hash/grid;
- переиспользование placeholder-мешей;
- пересчёт только изменённых клеток;
- стабильные ID;
- object pool для временных обломков, если они добавляются.

## Вне текущего scope

Пока не реализовывать:

- настоящие GLB-модели;
- сложную физику обрушений;
- деформацию terrain;
- копание земли;
- реалистичную нагрузку и массу;
- произвольные углы построек;
- footprint кроме 1×1 и 2×2;
- сетевую репликацию новой системы, если сетевой код ещё не готов;
- полноценный navmesh по многоэтажным сооружениям;
- анимации строительства;
- красивые VFX.

Однако новая архитектура не должна намеренно блокировать добавление мультиплеера и моделей позже.

## Финальная проверка

После завершения:

1. Выполни чистую сборку проекта.
2. Запусти тесты.
3. Проверь форматирование.
